## บทคัดย่อ

ในวงจรชีวิตการพัฒนาซอฟต์แวร์ การทดสอบวิดเจ็ต (widget testing) เป็นกระบวนการที่มีความสำคัญอย่างยิ่งสำหรับการค้นหาและแก้ไขข้อบกพร่อง เพื่อยกระดับความน่าเชื่อถือของซอฟต์แวร์ก่อนส่งมอบ สิ่งนี้มีความสำคัญเป็นพิเศษในโดเมนของแอปพลิเคชันมือถือที่พัฒนาด้วย Flutter framework ซึ่งมีการเปลี่ยนแปลงอยู่อย่างรวดเร็ว และมีการเปลี่ยนแปลงข้อกำหนดบ่อยครั้ง แม้ว่าการทดสอบอัตโนมัติจะช่วยลดเวลาทดสอบโดยรวม แต่นักพัฒนายังคงต้องมีความรู้เฉพาะทางและใช้ความพยายามเริ่มต้นอย่างมากในการสร้างสคริปต์ทดสอบที่มีประสิทธิภาพด้วยภาษา Dart

งานวิจัยนี้นำเสนอเครื่องมืออัตโนมัติที่ช่วยลดความซับซ้อนในการสร้างสคริปต์ทดสอบ Flutter โดยนำเข้าไฟล์ซอร์สโค้ดส่วน front-end, ดึงข้อมูลเมตาของวิดเจ็ต (คีย์, เงื่อนไขการตรวจสอบ, และประเภทการจัดการข้อมูลนำเข้า) และสร้างข้อมูลทดสอบสังเคราะห์ผ่าน Large Language Model (LLM) กรณีทดสอบถูกสร้างอย่างเป็นระบบโดยใช้เทคนิค Pairwise testing ผ่านเครื่องมือ PICT สคริปต์ทดสอบ Dart ที่ได้สามารถรันได้ทันทีบน Flutter testing framework

เครื่องมือนี้ถูกประเมินผลกับแอปพลิเคชันมือถือในโลกจริงสามรายการ ได้แก่ ระบบนัดหมายทางการแพทย์, แอปพลิเคชันรายชื่องาน, และแอปพลิเคชันรายชื่ออสังหาริมทรัพย์ และสามารถบรรลุ statement coverage ที่สูงกว่า 91% ในทุกหน้าจอที่ประเมิน ซึ่งแสดงให้เห็นถึงประสิทธิผลเชิงปฏิบัติของแนวทางที่นำเสนอ

## I. บทนำ

อุตสาหกรรมซอฟต์แวร์ระดับโลกยังคงเติบโตอย่างรวดเร็ว ขับเคลื่อนด้วยความต้องการแอปพลิเคชันมือถือที่มีความซับซ้อน มีฟีเจอร์หลากหลาย และมีการเปลี่ยนแปลงข้อกำหนดบ่อยครั้ง การประกันคุณภาพซอฟต์แวร์ผ่านการทดสอบที่ครอบคลุมจึงเป็นสิ่งจำเป็น แต่การออกแบบกรณีทดสอบด้วยตนเองนั้นใช้เวลานานและต้องอาศัยความเชี่ยวชาญอย่างลึกซึ้งจากนักพัฒนา

ภายใน Flutter framework นักพัฒนาเขียนสคริปต์ทดสอบแบบ integration และ widget ด้วยภาษา Dart เพื่อจำลองการโต้ตอบของผู้ใช้กับส่วนต่อประสานผู้ใช้ (UI) อย่างไรก็ตาม การสร้างสคริปต์เหล่านี้ต้องการให้นักพัฒนา (1) เข้าใจโครงสร้างวิดเจ็ตและกฎการตรวจสอบในซอร์สโค้ด (2) กำหนดข้อมูลนำเข้าที่เหมาะสมครอบคลุมเงื่อนไขขอบเขตทั้งที่ถูกต้องและไม่ถูกต้อง และ (3) จัดลำดับการทดสอบอย่างถูกต้อง เครื่องมืออัตโนมัติที่มีอยู่เช่น Robot Framework และ Playwright ถูกออกแบบมาสำหรับแอปพลิเคชันเว็บ และไม่สามารถสร้างสคริปต์ทดสอบเฉพาะสำหรับ Flutter ได้โดยตรง

งานวิจัยนี้แก้ไขปัญหาเหล่านี้โดยนำเสนอเครื่องมืออัตโนมัติที่:

- **วิเคราะห์** ไฟล์ Flutter front-end (`.dart`) เพื่อดึงข้อมูลเมตาของวิดเจ็ต
- **ใช้** Large Language Model (LLM) (Google Gemini) เพื่อสร้างข้อมูลทดสอบที่สมจริง
- **ประยุกต์ใช้** เทคนิค Pairwise testing ผ่าน PICT (Pairwise Independent Combinatorial Testing) เพื่อลดจำนวนกรณีทดสอบในขณะที่เพิ่มความครอบคลุมของการรวมกันของข้อมูลนำเข้าให้สูงสุด
- **ส่งออก** สคริปต์ทดสอบ Dart ที่สามารถรันได้ พร้อมใช้กับ Flutter testing framework

งานวิจัยนี้มุ่งตอบคำถามวิจัย (RQ) สองข้อ ซึ่งจะอธิบายในหัวข้อ V:

- **RQ1:** สคริปต์ทดสอบที่สร้างขึ้นอัตโนมัติสามารถบรรลุ statement coverage เท่าใดบนหน้าจอ Flutter ในโลกจริง โดยไม่ต้องเขียนกรณีทดสอบด้วยตนเอง?
- **RQ2:** เทคนิค pairwise ต้องการกรณีทดสอบจำนวนเท่าใดเมื่อเปรียบเทียบกับการทดสอบแบบ exhaustive combinatorial?

โครงสร้างที่เหลือของบทความนี้จัดไว้ดังนี้: หัวข้อ II ทบทวนงานวิจัยที่เกี่ยวข้อง หัวข้อ III อธิบายระเบียบวิธีที่นำเสนอ หัวข้อ IV อภิปรายการออกแบบเครื่องมือ หัวข้อ V นำเสนอผลการประเมิน และหัวข้อ VI สรุปบทความ

## II. งานวิจัยที่เกี่ยวข้อง

### A. การทดสอบ Flutter

Flutter คือ UI toolkit แบบ open-source ของ Google สำหรับสร้างแอปพลิเคชันข้ามแพลตฟอร์มจากโค้ดเบส Dart เดียว framework นี้มีไลบรารี `flutter_test` ซึ่งเปิดเผย API ของ `WidgetTester` และชุด Finders ที่หลากหลาย (`find.byKey`, `find.byType`, ฯลฯ) สำหรับการค้นหาและโต้ตอบกับวิดเจ็ตระหว่างการทดสอบ

### B. การสร้างสคริปต์ทดสอบจากไฟล์ Front-End

Ekakrachawakitti นำเสนอวิธีการสร้างสคริปต์ทดสอบสำหรับ Robot Framework จากไฟล์ front-end ของเว็บ โดยดึง HTML elements และข้อจำกัดข้อมูลนำเข้าจาก database schema Srivichayanun ขยายแนวคิดนี้โดยนำเข้า XML Schema Definition (XSD) schemas และใช้ Boundary Value Analysis เพื่อสร้างข้อมูลทดสอบสำหรับแอปพลิเคชันเว็บ งานวิจัยเหล่านี้เป็นแรงจูงใจในการปรับเทคนิคการดึงข้อมูลแบบเดียวกันมาใช้กับโครงสร้างวิดเจ็ตที่ใช้ Dart ของ Flutter

### C. การสร้างข้อมูลด้วย LLM

Tuan Pham แสดงให้เห็นว่าการจัดโครงสร้าง prompt ของ LLM ด้วยองค์ประกอบที่แตกต่างกัน ได้แก่ context, objective, style, target, execution, และ polish ช่วยปรับปรุงคุณภาพของผลลัพธ์ที่สร้างขึ้นได้อย่างมีนัยสำคัญ กลยุทธ์วิศวกรรม prompt นี้ถูกนำมาใช้ในงานวิจัยปัจจุบันเพื่อขับเคลื่อนการสร้างข้อมูลทดสอบสังเคราะห์

### D. Pairwise Testing

Pairwise (all-pairs) testing เป็นเทคนิคการออกแบบกรณีทดสอบแบบ black-box ที่รับประกันว่าทุกคู่ของค่าพารามิเตอร์นำเข้าจะถูกทดสอบอย่างน้อยหนึ่งกรณีทดสอบ ช่วยลดการระเบิดของชุดค่าผสมจากการครอบคลุมแบบเต็มรูปแบบได้อย่างมาก PICT เป็นเครื่องมือ open-source ที่ใช้กันอย่างแพร่หลาย ซึ่งรับไฟล์โมเดลที่อธิบายพารามิเตอร์และระดับค่าของมัน แล้วส่งออกชุดกรณีทดสอบที่ครอบคลุมขั้นต่ำ

## III. ระเบียบวิธีที่นำเสนอ

เครื่องมือที่นำเสนอทำให้กระบวนการสร้างสคริปต์ทดสอบตั้งแต่ต้นจนจบเป็นแบบอัตโนมัติ ผ่านสี่ขั้นตอนต่อเนื่อง ดังแสดงในรูปที่ 1

### ขั้นตอนที่ 1 — ดึง Manifest

เครื่องมือวิเคราะห์แบบ static ทุกไฟล์ `.dart` ภายใต้ไดเรกทอรี `lib/` ของ Flutter project เป้าหมาย เฉพาะวิดเจ็ตที่มี property `Key` เท่านั้นที่จะถูกพิจารณา เนื่องจากคีย์จำเป็นสำหรับการค้นหาวิดเจ็ตระหว่างการรันทดสอบผ่าน `find.byKey()`

ในระดับ **หน้าจอ (screen level)** เครื่องมือบันทึก metadata ของ BLoC/Cubit ที่จำเป็นสำหรับการสร้างสภาพแวดล้อมทดสอบ ได้แก่: ชื่อคลาสวิดเจ็ตของหน้า (`pageClass`), คลาส Cubit (`cubitClass`), คลาส State ที่เกี่ยวข้อง (`stateClass`), และพาธไปยังไฟล์ซอร์สของ Cubit และ State (`fileCubit`, `fileState`) ฟิลด์เหล่านี้ช่วยให้สคริปต์ทดสอบที่สร้างขึ้นสามารถ import ไฟล์ที่ถูกต้องและสร้าง wrapper `BlocProvider` ได้อัตโนมัติ

ในระดับ **วิดเจ็ต (widget level)** เครื่องมือบันทึก: (i) คีย์วิดเจ็ตที่ไม่ซ้ำกัน (ii) ชื่อคลาสวิดเจ็ต และ metadata เฉพาะประเภทในบล็อก `meta` สำหรับ `TextFormField` บล็อก `meta` บรรจุรูปแบบตัวอักษรที่อนุญาต (`inputFormatters`), ความยาวนำเข้าสูงสุด (`maxLength`), และกฎการตรวจสอบพร้อมข้อความแสดงข้อผิดพลาด (`validatorRules`) สำหรับ `DropdownButtonFormField` บรรจุรายการตัวเลือก (`options`) สำหรับ `Radio` บรรจุค่า enum ที่ปุ่มนั้นแทน (`valueExpr`) และการผูกสถานะร่วมของกลุ่ม radio (`groupValueBinding`) สำหรับ `Switch` และ `Checkbox` บรรจุการผูกสถานะปัจจุบัน (`valueBinding`)

คีย์วิดเจ็ตปฏิบัติตามรูปแบบการตั้งชื่อ `<prefix>_<seq>_<desc>_<type>` (เช่น `appt_01_patient_name_textfield`) โดย `seq` เป็นจำนวนเต็มที่มีเลขศูนย์นำหน้า ซึ่งขั้นตอนที่ 3 ใช้เพื่อจัดลำดับขั้นตอนการโต้ตอบกับวิดเจ็ต วิดเจ็ตที่มีคีย์ลงท้ายด้วย `_expected_success`, `_dialog_success`, `_expected_fail`, หรือ `_dialog_fail` จะถูกกำหนดให้เป็นเป้าหมายการยืนยันผลลัพธ์ ขั้นตอนที่ 3 จะสร้างการยืนยัน `byKey` สำหรับวิดเจ็ตเหล่านี้แทนที่จะรวมเป็นปัจจัย PICT

metadata ที่ดึงมาได้จะถูกบันทึกเป็นไฟล์ `manifest.json` จัดกลุ่มตามชื่อหน้าจอ ตารางที่ I แสดงฟิลด์ที่บันทึกต่อหน้าจอและต่อวิดเจ็ต

**ตารางที่ I: ฟิลด์ข้อมูลเมตาในไฟล์ Manifest**

### ขั้นตอนที่ 2 — สร้าง Datasets

ในขั้นตอนนี้จะดึงเฉพาะวิดเจ็ต `TextFormField` จาก manifest เท่านั้น

metadata ที่กรองแล้วจะถูกประกอบเป็น prompt ที่มีโครงสร้างตามกรอบงานหกองค์ประกอบของ Tuan Pham (context, target, objective, execution, style, polish) กฎ objective หลักสั่งให้โมเดลวิเคราะห์ `maxLength`, `inputFormatters`, และ `validatorRules`; ข้ามการตรวจสอบ `isEmpty`/`null` (จัดการโดยการสร้าง edge-case ในขั้นตอนที่ 3); สร้างคู่ valid/invalid หนึ่งคู่ต่อกฎที่ไม่ว่างเปล่าหนึ่งข้อ; รับประกันว่าค่า invalid ยังคงสอดคล้องกับ `inputFormatters`; และส่งคืน JSON ที่ถูกต้อง ตัวอย่าง few-shot สองตัวอย่างในส่วน execution กำหนด output schema และป้องกันค่าที่ LLM สร้างขึ้นเองโดยไม่มีหลักฐาน metadata ของวิดเจ็ตจากขั้นตอนที่ 1 ถูกแนบไปเป็น payload ข้อมูลนำเข้า

prompt ถูกส่งไปยัง Google Gemini 2.5 Flash ผ่าน Gemini API (HTTP POST) โมเดลส่งคืนไฟล์ `<page>.datasets.json` ซึ่งฟิลด์ระดับบนสุดประกอบด้วย:

- **file:** พาธไปยังไฟล์ซอร์ส front-end ที่วิเคราะห์
- **datasets → byKey:** แผนที่จากคีย์วิดเจ็ต `TextFormField` แต่ละตัวไปยังอาร์เรย์ของออบเจ็กต์คู่ค่า โดยสร้างหนึ่งคู่ต่อกฎการตรวจสอบที่ไม่ว่างเปล่าหนึ่งข้อ แต่ละออบเจ็กต์มีห้าฟิลด์:
  - `valid` — ค่าที่ผ่านทุกกฎการตรวจสอบและสอดคล้องกับ `inputFormatters`
  - `invalid` — ค่าที่ละเมิดกฎหนึ่งข้อในขณะที่ยังสอดคล้องกับ `inputFormatters` รับประกันว่าผู้ใช้ยังพิมพ์ได้
  - `invalidRuleMessages` — ข้อความแสดงข้อผิดพลาดเฉพาะที่ validator ที่ถูกละเมิดจะแสดง
  - `atMax` — ค่าขอบเขตที่ความยาวหรือขีดจำกัดสูงสุดที่อนุญาต (ข้อมูล edge-case)
  - `atMin` — ค่าขอบเขตที่ความยาวหรือขีดจำกัดต่ำสุดที่อนุญาต (ข้อมูล edge-case)

### ขั้นตอนที่ 3 — สร้าง Test Data

โดยใช้ datasets ที่สร้างในขั้นตอนที่ 2 (รูปที่ 3) เครื่องมือสร้างไฟล์โมเดล PICT ซึ่งวิดเจ็ตที่ไม่ใช่ปุ่มแต่ละตัวจะถูกแมปไปยัง **factor** หนึ่งตัว และแต่ละค่าที่แตกต่างกันจะถูกแมปไปยัง **level** หนึ่งตัว โมเดลสามแบบถูกสร้างแยกกัน:

1. **Invalid (IV):** ปัจจัย `TextFormField` บรรจุเฉพาะระดับ `invalid` sentinel; ปัจจัยที่ไม่ใช่ข้อความ (`Dropdown`, `Radio`, `Checkbox`, `Switch`) แจกแจงค่าตัวเลือกทั้งหมด ดังนั้นทุกชุดค่าผสมของ PICT จะมีข้อมูลข้อความ invalid อย่างน้อยหนึ่งรายการ ทำให้เกิดกรณีทดสอบแบบ negative-path
2. **Valid (V):** ปัจจัยบรรจุเฉพาะระดับ valid; PICT สร้างกรณีทดสอบแบบ positive-path
3. **Edge:** ชุดค่าผสมขอบเขตที่สร้างด้วยตนเองสามรายการ (ข้อมูลว่าง, ความยาวสูงสุด, ความยาวต่ำสุด) ถูกแนบต่อท้าย

ก่อนเรียกใช้ PICT นักพัฒนาอาจระบุ **constraint file** (`<page>.constraints.txt`) ที่เป็นทางเลือก ซึ่งเข้ารหัสกฎ business-logic ที่มองไม่เห็นผ่านการวิเคราะห์แบบ static รูปแบบไวยากรณ์สามแบบได้รับการรองรับ: (1) `<key>.valid = <value>` และ (2) `<key>.invalid = <value>` กำหนดสตริงที่แน่นอนใน `<page>.datasets.json` ก่อนที่ PICT จะรัน โดยไม่แตะต้องโมเดล; (3) `IF [keyA] = "v" THEN [keyB] = "v";` เพิ่มกฎข้ามวิดเจ็ตไปยังทั้งสองไฟล์โมเดลเพื่อให้ PICT สร้างเฉพาะชุดค่าผสมที่ตรงตามเงื่อนไข ข้อผิดพลาดทางไวยากรณ์จะทำให้แสดงข้อความ "Invalid Constraint Syntax" และหยุดการทำงานของ pipeline

PICT ถูกเรียกใช้เป็น subprocess หนึ่งครั้งต่อไฟล์โมเดล (`<page>.invalid.model.txt` สำหรับ IV และ `<page>.valid.model.txt` สำหรับ V) ผลลัพธ์ที่คั่นด้วย tab ของ PICT ดังแสดงในรูปที่ 2 ถูกวิเคราะห์ และแต่ละแถวถูกประกอบเป็นออบเจ็กต์ case พร้อมกับขั้นตอนการโต้ตอบกับวิดเจ็ตและการยืนยันผลที่คาดหวัง

อาร์เรย์ผลลัพธ์สาม (IV, V, Edge) ถูกรวมเป็นไฟล์ `<page>.test_data.json` ไฟล์เดียวที่มีสามคีย์ระดับบนสุด:

- **source:** metadata ของ BLoC ระดับหน้าจอที่ส่งต่อมาจากขั้นตอนที่ 1 (`pageClass`, `cubitClass`, `stateClass`, `fileCubit`, `fileState`) ขั้นตอนที่ 4 อ่านคีย์นี้เพื่อสร้าง statement `import` และสร้าง wrapper `BlocProvider`
- **datasets:** คู่ค่า valid/invalid ที่สร้างในขั้นตอนที่ 2 จัดกลุ่มตามคีย์วิดเจ็ต (`byKey`) ขั้นตอนที่ 4 อ่านคีย์นี้เพื่อแก้ไขค่าที่เป็นรูปธรรมเมื่อแสดงผลการเรียก `enterText`
- **cases:** รายการที่เรียงลำดับของออบเจ็กต์กรณีทดสอบ ดังแสดงตัวอย่างในรูปที่ 5 แต่ละออบเจ็กต์มีห้าฟิลด์: `tc` (ตัวระบุที่ไม่ซ้ำกัน เช่น `pairwise_invalid_cases_1`), `kind` (`success` หรือ `failed`), `group` (หนึ่งใน `pairwise_invalid_cases`, `pairwise_valid_cases`, หรือ `edge_cases`), `steps`, และ `asserts`

แต่ละรายการ `steps` แมปประเภทวิดเจ็ตไปยังคำสั่ง `WidgetTester`: `enterText` (พร้อม `byKey` และการอ้างอิง `dataset`) สำหรับ `TextFormField`; `tap` (byKey) แล้ว `tapText` (label รายการ) สำหรับ `DropdownButtonFormField`; `tap` (byKey) สำหรับ `Radio`, `Checkbox`, และ `Switch`; และ `pump` หรือ `pumpAndSettle` สำหรับการรีเฟรช UI ขั้นตอนของวิดเจ็ตเรียงลำดับตามค่า `sequence` ที่ดึงมาจากไฟล์ซอร์ส โดย `ElevatedButton` จะถูกวางไว้เสมอ แต่ละรายการ `asserts` ระบุสตริง `text` พร้อม flag `exists` (ตรวจสอบข้อความแสดงข้อผิดพลาดที่มองเห็น) หรือตัวระบุวิดเจ็ต `byKey` พร้อม flag `exists` (ตรวจสอบการมีอยู่ของวิดเจ็ตตัวบ่งชี้ความสำเร็จหรือล้มเหลว)

ตารางที่ II สรุปว่าวิดเจ็ตแต่ละประเภทที่รองรับถูกแมปไปยังบทบาท PICT และคำสั่งโต้ตอบ `WidgetTester` ที่สอดคล้องกันอย่างไร

**ตารางที่ II: วิดเจ็ต Flutter ที่รองรับและการโต้ตอบในการทดสอบที่สร้างขึ้น**

| วิดเจ็ต | บทบาทใน PICT | คำสั่งทดสอบ |
|---------|-------------|------------|
| `TextFormField` | Factor {valid, invalid} | `enterText` |
| `DropdownButtonFormField` | Factor (enum) | `tap` ×2 |
| `Radio` | Factor (enum) | `tap` |
| `Checkbox` | Factor {checked, unchecked} | `tap` |
| `Switch` | Factor {on, off} | `tap` |
| `ElevatedButton` | Trigger (fixed) | `tap` (สุดท้าย) |

### ขั้นตอนที่ 4 — สร้างสคริปต์ทดสอบ

`<page>.test_data.json` ที่สร้างในขั้นตอนที่ 3 ถูกแสดงผลเป็นไฟล์ทดสอบ Dart ที่ถูกต้องทางไวยากรณ์ชื่อ `<page>_test.dart` คลาส `TestScriptGenerator` อ่านคีย์ **source** ก่อนเพื่อสร้าง statement `import` สาม statement (`fileCubit`, `fileState`, และไฟล์ซอร์สของหน้า) และประกาศ wrapper `BlocProvider<CubitClass>` ที่ใช้ซ้ำในกรณีทดสอบทั้งหมดบนหน้าจอเดียวกัน

กรณีทดสอบถูกแบ่งตามฟิลด์ `group` เป็นสาม block `group()` ในไฟล์ output: `pairwise_invalid_cases` (กรณี IV ที่ตรวจสอบการปฏิเสธฟอร์มบนข้อมูลนำเข้าที่ไม่ถูกต้อง), `pairwise_valid_cases` (กรณี V ที่ตรวจสอบการส่งที่สำเร็จบนข้อมูลนำเข้าที่ถูกต้อง), และ `edge_cases` (กรณีค่าขอบเขต) แต่ละรายการในอาร์เรย์ `cases` กลายเป็น block `testWidgets` อิสระหนึ่งตัวที่ตั้งชื่อตามตัวระบุ `tc` ของมัน โดยมีโครงสร้างสามขั้นตอน:

1. **Setup:** `tester.pumpWidget()` สร้าง `MaterialApp` พร้อมหน้าที่ห่อใน `BlocProvider` จาก metadata ของ `source`
2. **Interact:** แต่ละรายการ `steps` ถูกแปลเป็นการเรียก `WidgetTester` ที่สอดคล้องกันตามลำดับ โดย `enterText` แก้ไขค่าจากคีย์ `datasets` และ `pumpAndSettle` ซิงโครไนซ์ UI; การ tap `ElevatedButton` อยู่เสมอ
3. **Assert:** แต่ละรายการ `asserts` กลายเป็นการเรียก `expect()` โดยใช้ `findsOneWidget` หรือ `findsNothing` ตาม flag `exists`

## IV. การออกแบบและการพัฒนาเครื่องมือ

### A. ส่วนต่อประสานผู้ใช้

รูปที่ 4 แสดงหน้าต่างหลักของเครื่องมือ ส่วนต่อประสานมีข้อมูลนำเข้าสามรายการและการดำเนินการหนึ่งรายการที่ครอบคลุมขั้นตอนการสร้างกรณีทดสอบทั้งหมด:

1. **ไฟล์ Flutter front-end:** file-picker สำหรับไฟล์หน้าจอ `.dart` เป้าหมาย เครื่องมือตรวจสอบประเภทไฟล์และยืนยันว่ามีวิดเจ็ตที่รองรับและมีคีย์อย่างน้อยหนึ่งตัว; ประเภทไฟล์ที่ไม่รองรับจะแสดงข้อความ "Invalid File Type" และบล็อกการประมวลผลต่อไป
2. **ไฟล์เงื่อนไข (ทางเลือก):** file-picker ที่สองสำหรับไฟล์ constraint PICT ที่เป็นทางเลือก เขียนด้วยไวยากรณ์ `IF...THEN...` หากระบุ เครื่องมือจะตรวจสอบไวยากรณ์ constraint ก่อนดำเนินการต่อ; ไฟล์ที่รูปแบบผิดจะแสดงข้อความ "Invalid Constraint Syntax"
3. **ไดเรกทอรีผลลัพธ์:** directory-picker ที่กำหนดโฟลเดอร์ปลายทางสำหรับ artifacts ที่สร้างขึ้นทั้งหมด ได้แก่ `manifest.json`, `datasets.json`, `test_data.json`, และ `<page>_test.dart`
4. **ปุ่ม Generate:** การคลิก Generate จะเรียก pipeline สี่ขั้นตอนเต็มรูปแบบ สถานะความคืบหน้าและข้อความแสดงข้อผิดพลาดใดๆ จะแสดงในหน้าต่างหลัก

### B. การติดตั้ง

ต้องมีสิ่งที่จำเป็นต่อไปนี้ก่อนใช้เครื่องมือ:

1. **Docker** (v28.0.0 หรือใหม่กว่า): เริ่ม back-end container ซึ่งโฮสต์บริการ FastAPI (v0.114.1) ที่เปิดเผย REST endpoints สำหรับแต่ละขั้นตอนของ pipeline ด้วยคำสั่ง `docker run -p 8000:8000 <image>`
2. **PICT:** ติดตั้ง Microsoft PICT binary และรับประกันว่าสามารถเข้าถึงได้บน system `PATH` เครื่องมือเรียกใช้ PICT เป็น subprocess ในขั้นตอนที่ 3
3. **Gemini API key:** กำหนดค่าคีย์เป็นตัวแปรสภาพแวดล้อมหรือป้อนในแผงการตั้งค่าเครื่องมือ คีย์จำเป็นสำหรับการเรียก LLM ในขั้นตอนที่ 2
4. **Web browser:** รัน `bash run_tool.sh` เพื่อเริ่ม web interface server จากนั้นเปิดเบราว์เซอร์และไปที่ `http://localhost:8080` เพื่อเข้าถึงเครื่องมือ

### C. วิดเจ็ตที่รองรับ

เวอร์ชันปัจจุบันรองรับวิดเจ็ตหกประเภท ดังรายละเอียดในตารางที่ II วิดเจ็ตห้าประเภททำหน้าที่เป็นปัจจัย PICT (`TextFormField`, `DropdownButtonFormField`, `Radio`, `Checkbox`, `Switch`) และหนึ่งประเภทเป็น trigger คงที่ (`ElevatedButton`) การยืนยันผลลัพธ์ไม่ผูกกับประเภทวิดเจ็ตเฉพาะ; แทนที่จะเป็นเช่นนั้น วิดเจ็ตใดก็ตามที่มีคีย์ลงท้ายด้วย `_expected_success`, `_dialog_success`, `_expected_fail`, หรือ `_dialog_fail` จะถูกกำหนดให้เป็นเป้าหมายการยืนยันที่ตรวจสอบผ่าน `find.byKey`

### D. การสร้างโมเดล PICT

สำหรับหน้าจอที่มีวิดเจ็ตที่ไม่ใช่ปุ่ม n ตัว ไฟล์โมเดล PICT จะมี n บรรทัดพารามิเตอร์ในรูปแบบ `<key>: v1, v2, ..., vk` โดย vi แต่ละตัวคือระดับค่าที่แตกต่างกัน เครื่องมือสร้างไฟล์โมเดล PICT สองไฟล์ (IV และ V) และเรียกใช้ PICT หนึ่งครั้งต่อไฟล์ การรัน PICT แต่ละครั้งส่งคืนอาร์เรย์ครอบคลุมขั้นต่ำ; สองอาร์เรย์ถูกเชื่อมต่อพร้อมสาม edge cases ที่กำหนดไว้แบบ hardcoded เพื่อสร้างชุดทดสอบที่สมบูรณ์สำหรับหน้าจอ

### E. ข้อจำกัดของการพัฒนา

สคริปต์ที่สร้างขึ้นแต่ละตัวครอบคลุม **หนึ่ง** หน้าจอแอปพลิเคชันต่อการรันหนึ่งครั้ง วิดเจ็ตเป้าหมายทุกตัวต้องมี property `Key` ที่ไม่ซ้ำกัน; วิดเจ็ตที่ไม่มีคีย์จะถูกข้ามอย่างเงียบๆ การเรียก LLM ต้องการ Gemini API key ที่ถูกต้องขณะรัน และ PICT ต้องติดตั้งและเข้าถึงได้บน system `PATH`

## V. การประเมินผล

### A. การตั้งค่าการทดลอง

เครื่องมือถูกประเมินกับแอปพลิเคชัน Flutter ในโลกจริงสามรายการ: แอป **Medical Appointment** (นัดหมายทางการแพทย์), แอป **Job Listing** (รายชื่องาน), และแอป **Real-Estate Listing** (รายชื่ออสังหาริมทรัพย์) เลือกสองหน้าจอต่อแอปพลิเคชัน ส่งผลให้มีการประเมินระดับหน้าจอทั้งหมดหกรายการ สภาพแวดล้อมทดสอบใช้ Flutter v3.27.3 รันบน macOS Sequoia 15.4.1 Statement coverage วัดโดยใช้ flag Flutter `--coverage` รวมกับ `lcov` เพื่อกรองผลลัพธ์ไปยังไฟล์หน้า UI เท่านั้น

### B. ภาพรวม Case Studies

แอปพลิเคชันสามรายการแสดงถึงความซับซ้อนของการตรวจสอบฟอร์มที่เพิ่มขึ้น:

- แอป **Medical Appointment** มีหน้าจอการจองพร้อมวิดเจ็ตนำเข้าเก้าตัว (TextFormField, DropdownButtonFormField, Radio, Switch) และหน้าจอค้นหาที่เบากว่า ให้กรณีทดสอบ 52 กรณี (28 IV, 21 V, 3 Edge) และ 6 กรณี (2 IV, 1 V, 3 Edge) ตามลำดับ
- แอป **Job Listing** มีหน้าจอโพสต์งานพร้อมกฎการตรวจสอบข้ามฟิลด์ที่ซับซ้อน (เช่น ข้อจำกัดช่วงเงินเดือน) สร้าง 64 กรณี (31 IV, 30 V, 3 Edge) สำหรับการโพสต์และ 63 กรณี (30 IV, 30 V, 3 Edge) สำหรับการค้นหา แสดงให้เห็นว่า pairwise ปรับตัวเข้ากับข้อจำกัดที่หนาแน่นได้ตามธรรมชาติ
- แอป **Real-Estate Listing** นำเสนอสองหน้าจอที่มีความซับซ้อนใกล้เคียงกัน แต่ละหน้าสร้าง 55 กรณี (27 IV, 25 V, 3 Edge) ยืนยันจำนวนกรณีที่เสถียรสำหรับรายการวิดเจ็ตที่เทียบเคียงกัน

รูปที่ 5 แสดงกรณี IV ที่สร้างขึ้นหนึ่งรายการ

### C. ผลการครอบคลุม

ตารางที่ III สรุป statement coverage และจำนวนกรณีทดสอบในทั้งหกหน้าจอที่ประเมิน ตารางที่ IV แสดงรายละเอียดการแบ่ง IV, V, และ Edge ต่อหน้าจอ ทุกหน้าจอบรรลุ statement coverage สูงกว่า **91%** และผลลัพธ์สูงสุด (**96.6%**, Real-Estate posting) ได้รับแม้จะมีจำนวนกรณีทดสอบที่ลดลง

คุณลักษณะสามประการของสคริปต์ที่สร้างขึ้นมีส่วนให้ผลนี้:
1. ทุก widget interaction ใช้ `find.byKey` ซึ่งให้ locator ที่เสถียรซึ่งทนต่อการ refactor UI
2. ทุก `validatorRule` ที่ไม่ว่างเปล่าขับเคลื่อนค่า invalid หนึ่งค่าบวกค่า valid หนึ่งค่าที่เป็นคู่ รับประกันว่าแต่ละ branch การตรวจสอบใน Cubit ถูกทดสอบอย่างน้อยหนึ่งครั้ง
3. ทั้งกลุ่ม IV และ V ถูกสร้างในการเรียกใช้เดียว ให้ทีมครอบคลุม positive และ negative test paths ทันที

### D. คำตอบต่อคำถามวิจัย

**RQ1 — Coverage ที่บรรลุ:**
ตารางที่ III ยืนยันว่าทุกหน้าจอเกิน 91% statement coverage โดยไม่ต้องเขียนกรณีทดสอบด้วยตนเอง โดยสูงสุดอยู่ที่ 96.6% สำหรับหน้าจอ Real-Estate posting ปัจจัยสามประการมีส่วนให้ผลนี้: (i) locator `find.byKey` ทนต่อการ refactor UI; (ii) ทุก `validatorRule` ที่ไม่ว่างเปล่าขับเคลื่อนคู่ invalid–valid อย่างน้อยหนึ่งคู่ รับประกันว่าแต่ละ branch การตรวจสอบถูกทดสอบ; และ (iii) ทั้งกลุ่ม IV และ V ถูกสร้างในการเรียกใช้เดียว ครอบคลุม positive และ negative paths พร้อมกัน

**RQ2 — การลดจำนวนเชิง Combinatorial:**
ตารางที่ V เปรียบเทียบจำนวน exhaustive combinatorial กับจำนวน pairwise IV สำหรับแต่ละหน้าจอ การลดจำนวนปรับขนาดตามจำนวนพารามิเตอร์: หน้าจอที่มีปัจจัยเดียวไม่มีการลด ในขณะที่หน้าจอที่มี 11–12 ปัจจัยบรรลุการลดสามลำดับขนาด (991× สำหรับ Job-Listing posting; 3,413× สำหรับ Real-Estate posting) ยืนยันว่า pairwise จำเป็นสำหรับการรักษา test suites ให้จัดการได้เมื่อความซับซ้อนของฟอร์มเพิ่มขึ้น

## VI. บทสรุป

บทความนี้นำเสนอเครื่องมืออัตโนมัติสำหรับสร้างสคริปต์ทดสอบ Flutter widget โดยใช้การผสมผสานของการดึงข้อมูลเมตาจากซอร์สโค้ด, การสร้างข้อมูลสังเคราะห์ขับเคลื่อนด้วย LLM, และเทคนิค Pairwise testing เครื่องมือนี้ไม่ต้องการการเขียนกรณีทดสอบด้วยตนเอง: นักพัฒนาให้เฉพาะไฟล์ Flutter front-end และรับสคริปต์ทดสอบ Dart ที่พร้อมรัน การประเมินกับแอปพลิเคชันมือถือในโลกจริงสามรายการยืนยันว่าเครื่องมือสร้างสคริปต์ทดสอบที่รันได้สำเร็จพร้อม code coverage ที่วัดได้

ข้อจำกัดในปัจจุบันรวมถึง: ชุดประเภทวิดเจ็ตที่รองรับที่คงที่, ขอบเขตหน้าจอเดียวต่อการรัน, และข้อกำหนดที่วิดเจ็ตเป้าหมายทุกตัวต้องมี `Key` ที่ไม่ซ้ำกัน งานวิจัยในอนาคตจะขยายการรองรับวิดเจ็ต, เปิดใช้งานการทดสอบ end-to-end หลายหน้าจอ, และนำแนวทางไปใช้กับ mobile framework อื่นๆ เช่น React Native และ SwiftUI
