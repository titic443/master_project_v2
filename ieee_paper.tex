\begin{abstract}
% -----------------------------------------------
In the software development lifecycle, unit testing is a critical process
for identifying and resolving defects, thereby enhancing software
reliability prior to delivery. This is particularly crucial in the rapidly
evolving domain of mobile applications developed with the Flutter framework,
where requirements change frequently. Although automated testing reduces
overall testing time, developers still require specialized knowledge and
significant initial effort to create effective test scripts in the Dart
language. This paper presents an automated tool that streamlines the
generation of Flutter test scripts by importing front-end source files,
extracting widget metadata (keys, validation conditions, and input-handling
types), and producing synthetic test data through a Large Language Model
(LLM). Test cases are systematically generated using the Pairwise testing
technique via the PICT tool. The resulting Dart test scripts are ready to
execute within the Flutter testing framework. The tool was evaluated against
three real-world mobile applications---a medical appointment system, a job
listing application, and a real-estate listing application---and achieved
above 91\% statement coverage across all evaluated screens, demonstrating the
practical effectiveness of the proposed approach.
\end{abstract}

\begin{IEEEkeywords}
Flutter, automated test generation, pairwise testing, Dart, large language
model, mobile application testing, PICT
\end{IEEEkeywords}

\section{Introduction}
% ===============================================

The global software industry continues to grow rapidly, driven by increasing
demand for mobile applications that are complex, feature-rich, and subject to
frequent requirement changes. Ensuring software quality through comprehensive
testing is therefore essential, yet designing test cases manually is
time-consuming and demands deep expertise from developers.

Within the Flutter framework \cite{b1}, developers write integration and
widget test scripts in Dart to simulate user interactions on the user interface (UI). However,
crafting these scripts requires developers to (1) understand widget structure
and validation rules in the source code, (2) define appropriate input data
covering valid and invalid boundary conditions, and (3) sequence test actions
correctly. Existing automation tools such as Robot Framework and Playwright
are tailored for web applications and cannot directly generate Flutter-specific
test scripts.

This paper addresses these challenges by proposing an automated tool that:
\begin{itemize}
  \item Parses Flutter front-end (\texttt{.dart}) files to extract widget
        metadata;
  \item Uses a Large Language Model (LLM) (Google Gemini) to synthesize realistic test data;
  \item Applies the Pairwise testing technique through PICT (Pairwise
        Independent Combinatorial Testing) to minimize the
        number of test cases while maximizing input-combination coverage;
  \item Outputs executable Dart test scripts ready for the Flutter testing
        framework.
\end{itemize}

The remainder of this paper is organized as follows. Section~II reviews
related work. Section~III describes the proposed methodology. Section~IV
discusses tool design. Section~V presents evaluation results, and
Section~VI concludes the paper.

% ===============================================
\section{Related Work}
% ===============================================

\subsection{Flutter Testing}
Flutter \cite{b1} is Google's open-source UI toolkit for building
cross-platform applications from a single Dart codebase. The framework
provides the \texttt{flutter\_test} library, which exposes a
\texttt{WidgetTester} application programming interface (API) and a rich set of Finders (\texttt{find.byKey},
\texttt{find.byType}, etc.) for locating and interacting with widgets during
testing.

\subsection{Test-Script Generation from Front-End Files}
Ekakrachawakitti \cite{b2} proposed a method for generating Robot Framework test
scripts from web front-end files by extracting HTML elements and input
constraints from a database schema. Srivichayanun \cite{b3} extended this concept
by importing XML Schema Definition (XSD) schemas and applying Boundary Value Analysis to produce test
data for web applications. These works motivate adapting similar extraction
techniques to Flutter's Dart-based widget structure.

\subsection{LLM-Based Data Generation}
Tuan Pham \cite{b4} demonstrated that structuring LLM prompts with distinct
components---context, objective, style, target, execution, and
polish---significantly improves the quality of generated outputs. This
prompt-engineering strategy is adopted in the present work to drive synthetic
test-data generation.

\subsection{Pairwise Testing}
Pairwise (all-pairs) testing \cite{b7} is a black-box test-design technique
that ensures every pair of input-parameter values is exercised by at least one
test case, dramatically reducing the combinatorial explosion of full coverage.
PICT \cite{b8} is a widely used
open-source tool that accepts a model file describing parameters and their
levels, and outputs a minimal covering test suite.

\subsection{Phase 1 -- Extract Manifest}

The tool statically analyzes every \texttt{.dart} file under the
\texttt{lib/} directory of the target Flutter project. Only widgets that
carry a \texttt{Key} property are considered, as the key is required to
locate a widget during test execution via \texttt{find.byKey()}.

At the \textit{screen level}, the tool records Business Logic Component (BLoC)/Cubit metadata required
to construct the test environment: the page widget class name
(\texttt{pageClass}), the Cubit class (\texttt{cubitClass}), the associated
State class (\texttt{stateClass}), and the paths to the Cubit and State
source files (\texttt{fileCubit}, \texttt{fileState}). These fields allow
the generated test script to import the correct files and instantiate a
\texttt{BlocProvider} wrapper automatically.

At the \textit{widget level}, the tool records: (i)~the unique widget key,
(ii)~the widget class name, (iii)~allowed character patterns from
\texttt{inputFormatters}, (iv)~the maximum input length
(\texttt{maxLength}) for \texttt{TextFormField} widgets, and
(v)~validation rules and error messages parsed from \texttt{validator}
callbacks (\texttt{validatorRules}).

The extracted metadata is serialized into a \texttt{manifest.json} file
grouped by screen name. Table~\ref{tab:manifest} lists the fields recorded
per screen and per widget.

\subsection{Phase 2 -- Generate Datasets}

Only \texttt{TextFormField} widgets are extracted from the manifest
for this phase; \texttt{Dropdown} and \texttt{Radio} widgets are
excluded because their enumerated levels are resolved directly from
the \texttt{options} list in Phase~1.

The filtered metadata is assembled into a structured prompt composed
of six components following the approach of Tuan Pham \cite{b4}:
\textit{context} (``Test data generator for Flutter form
validation.''), \textit{objective} (five rules: analyze \texttt{maxLength},
\texttt{inputFormatters}, and \texttt{validatorRules}; skip
\texttt{isEmpty}/\texttt{null} rules, which are handled separately by
edge-case generation in Phase~3; generate one valid/invalid pair per
nonempty rule; ensure invalid values still conform to
\texttt{inputFormatters} so they remain typeable; and output valid
JSON), \textit{style} (JSON only, no markdown, realistic values, string
arrays only), \textit{target} (instructs the model to act as a QA
engineer generating data for happy-path and error-path scenarios),
\textit{execution} (step-by-step counting procedure accompanied by two
few-shot examples that fix the output schema and prevent hallucinated
values), and \textit{polish} (output quality constraints ensuring
consistent schema adherence and no extraneous fields). The widget
metadata extracted in Phase~1 is appended as the input-data payload.

The prompt is submitted to \textit{Google Gemini 2.5 Flash}
\cite{b5} via the Gemini API (HTTP POST). The model returns a
\texttt{<page>.datasets.json} file whose top-level fields are:

\begin{itemize}
  \item \textbf{file:} path to the front-end source file analyzed.
  \item \textbf{datasets $\to$ byKey:} a map from each
        \texttt{TextFormField} widget key to an array of value-pair
        objects. One pair is produced per nonempty validation rule;
        each object contains five fields:
        \begin{itemize}
          \item \texttt{valid} --- a value that satisfies every
                validation rule and conforms to
                \texttt{inputFormatters};
          \item \texttt{invalid} --- a value that violates exactly
                one rule while still conforming to
                \texttt{inputFormatters}, ensuring it remains
                typeable by the user;
          \item \texttt{invalidRuleMessages} --- the specific error
                message that the violated validator would display;
          \item \texttt{atMax} --- a boundary value at the maximum
                allowed length or limit (edge-case data);
          \item \texttt{atMin} --- a boundary value at the minimum
                allowed length or limit (edge-case data).
        \end{itemize}
\end{itemize}

\subsection{Phase 3 -- Generate Test Data}

Using the datasets produced in Phase~2
(Fig.~\ref{fig:datasets}), the tool constructs a PICT model file in
which each nonbutton widget maps to one \textit{factor} and each
distinct value maps to one \textit{level}. Three model variants are
built independently:
\begin{enumerate}
  \item \textbf{Valid/Invalid (VI):} factors contain both valid and invalid
        levels; PICT ensures every valid--invalid pair is covered.
  \item \textbf{Valid-only (V):} factors contain valid levels only; PICT
        produces positive-path test cases.
  \item \textbf{Edge:} three manually crafted boundary-value combinations
        (empty input, maximum-length, special characters) are appended.
\end{enumerate}

Before invoking PICT, the developer may supply an optional
\textit{constraint file} (\texttt{<page>.constraints.txt}) that encodes
business-logic rules which reside in the Cubit layer and are therefore
invisible to static analysis of the front-end file alone. The tool
recognizes three mutually exclusive grammar forms, each dispatched to a
different stage of the pipeline:
\begin{enumerate}
  \item \textbf{Valid override (\texttt{<key>.valid = <value>}):}
        pins a specific \textit{valid} input value for a single widget key.
        On import, the tool overwrites the corresponding entry in
        \texttt{<page>.datasets.json}, so the pinned value replaces the
        LLM-generated sample before any PICT invocation takes place.
  \item \textbf{Invalid override (\texttt{<key>.invalid = <value>}):}
        pins an \textit{invalid} input value for a widget key using the
        same overwrite mechanism on \texttt{<page>.datasets.json}. Forms
        (1) and (2) therefore leave the PICT model untouched; they only
        change the concrete strings that Phase~4 eventually emits.
  \item \textbf{Cross-widget relation
        (\texttt{IF [key\textsubscript{A}] = "v\textsubscript{A}" THEN
        [key\textsubscript{B}] = "v\textsubscript{B}";}):} expresses a
        dependency between two widgets, optionally negated with
        \texttt{<>}. Rules of this form are appended as a
        \texttt{[Constraints]} section to both
        \texttt{<page>.invalid.model.txt} and
        \texttt{<page>.valid.model.txt}, and PICT is then asked to
        produce only combinations that satisfy them.
\end{enumerate}
This split gives the developer a lightweight way to encode
fixed-lookup values (forms 1--2) without having to reason about PICT
syntax, while still exposing the full expressive power of PICT
constraints (form 3) for mutual-exclusion or implication rules between
fields. The tool validates the grammar of every line before either
overwriting the datasets or appending to the model; a syntax error
triggers an \textit{``Invalid Constraint Syntax''} message and halts
the pipeline.

PICT is then invoked as a subprocess once per model file
(\texttt{<page>.invalid.model.txt} for VI and
\texttt{<page>.valid.model.txt} for V). Its tab-delimited
output---one row per test case, with one column per factor, as
illustrated in Fig.~\ref{fig:pict_result}---is parsed, and each row
is assembled into a \textit{case} object together with the widget
interaction steps and expected assertions. The three result arrays (VI, V, Edge) are then
merged into a single \texttt{<page>.test\_data.json} file that contains
three top-level keys:
\begin{itemize}
  \item \textbf{source:} the screen-level BLoC metadata propagated from
        Phase~1 (\texttt{pageClass}, \texttt{cubitClass},
        \texttt{stateClass}, \texttt{fileCubit}, \texttt{fileState}).
        Phase~4 reads this key to emit \texttt{import} statements and
        instantiate the \texttt{BlocProvider} wrapper.
  \item \textbf{datasets:} the valid/invalid value pairs produced in
        Phase~2, keyed by widget key (\texttt{byKey}). Phase~4 reads
        this key to resolve concrete values when rendering
        \texttt{enterText} calls.
  \item \textbf{cases:} the ordered list of test-case objects; a
        concrete example is shown in Fig.~\ref{fig:case_example}.
        Each object carries five fields: \texttt{tc} (a unique
        identifier such as \texttt{pairwise\_valid\_invalid\_cases\_1}),
        \texttt{kind} (\texttt{success} or \texttt{failed}),
        \texttt{group} (one of \texttt{pairwise\_valid\_invalid\_cases},
        \texttt{pairwise\_valid\_cases}, or \texttt{edge\_cases}),
        \texttt{steps}, and \texttt{asserts}.
\end{itemize}

Each \texttt{steps} entry maps widget type to a
\texttt{WidgetTester} command: \texttt{enterText} (with
\texttt{byKey} and a \texttt{dataset} reference) for
\texttt{TextFormField}; \texttt{tap} (byKey) then \texttt{tapText}
(item label) for \texttt{DropdownButtonFormField}; \texttt{tap}
(byKey) for \texttt{Radio}, \texttt{Checkbox}, and \texttt{Switch};
and \texttt{pump} or \texttt{pumpAndSettle} for UI refresh. Widget
steps are ordered by a \texttt{sequence} value extracted from the
source file, with the \texttt{ElevatedButton} step always placed last.
Each \texttt{asserts} entry specifies either a \texttt{text}
string with an \texttt{exists} flag (verifying a visible error message)
or a \texttt{byKey} widget identifier with an \texttt{exists} flag
(verifying the presence of a success or failure indicator widget).

\subsection{Phase 4 -- Generate Test Script}

The \texttt{<page>.test\_data.json} produced in Phase~3 is rendered
into a syntactically valid Dart test file named
\texttt{<page>\_test.dart}. The \texttt{TestScriptGenerator} class
first reads the \textbf{source} key to emit three \texttt{import}
statements (\texttt{fileCubit}, \texttt{fileState}, and the page
source file) and to declare a
\texttt{BlocProvider\textless CubitClass\textgreater} wrapper that is
reused across all test cases on the same screen.

Test cases are partitioned by their \texttt{group} field into three
\texttt{group()} blocks in the output file:
\texttt{pairwise\_valid\_invalid\_cases} (VI cases that verify form
rejection on invalid input), \texttt{pairwise\_valid\_cases} (V cases
that verify successful submission on valid input), and
\texttt{edge\_cases} (boundary-value cases). Each entry in the
\texttt{cases} array becomes one independent \texttt{testWidgets}
block named after its \texttt{tc} identifier. The block is structured
as follows:
\begin{enumerate}
  \item \textbf{Setup:} \texttt{tester.pumpWidget()} pumps a
        \texttt{MaterialApp} with the page wrapped in the
        \texttt{BlocProvider} declared from \texttt{source} metadata.
  \item \textbf{Interact:} each \texttt{steps} entry is translated
        to the corresponding \texttt{WidgetTester} call in sequence
        order---\texttt{enterText} resolves its value from the
        \texttt{datasets} key; \texttt{tap} and \texttt{tapText}
        locate widgets by key or label text; \texttt{pump} and
        \texttt{pumpAndSettle} synchronize the UI between interactions.
  \item \textbf{Assert:} each \texttt{asserts} entry is rendered as
        an \texttt{expect()} call. A \texttt{text}-based entry becomes
        \texttt{expect(find.text(`msg'),} \texttt{findsOneWidget)} and
        a \texttt{byKey}-based entry becomes
        \texttt{expect(find.byKey(Key(`k')),} \texttt{findsOneWidget)};
        the matcher switches between \texttt{findsOneWidget} and
        \texttt{findsNothing} according to the \texttt{exists} flag.
\end{enumerate}
The \texttt{ElevatedButton} step is always the last interaction,
followed by \texttt{pumpAndSettle()}, ensuring all asynchronous UI
updates settle before the assertions execute.

\section{Tool Design and Implementation}
% ===============================================

\subsection{User Interface}
Fig.~\ref{fig:ui_main} shows the main window of the tool. The interface
provides three inputs and one action that together cover the full
test-generation workflow:
\begin{enumerate}
  \item \textbf{Flutter front-end file:} A file-picker for the target
        \texttt{.dart} screen file. The tool validates the file type and
        confirms that at least one supported, keyed widget is present;
        an unsupported file type displays an \textit{``Invalid File
        Type''} message and blocks further processing.
  \item \textbf{Condition file (optional):} A second file-picker for an
        optional PICT constraint file written in
        \texttt{IF\ldots THEN\ldots} syntax. If supplied, the tool
        validates the constraint syntax before proceeding; a malformed
        file displays an \textit{``Invalid Constraint Syntax''} message.
  \item \textbf{Output directory:} A directory-picker that sets the
        destination folder for all generated artifacts---
        \texttt{manifest.json}, \texttt{datasets.json},
        \texttt{test\_data.json}, and \texttt{<page>\_test.dart}.
  \item \textbf{Generate button:} Clicking \textit{Generate} triggers
        the full four-phase pipeline. Progress status and any error
        messages are displayed inline in the main window.
\end{enumerate}

\subsection{Installation}
The following prerequisites must be in place before using the tool:
\begin{enumerate}
  \item \textbf{Docker} (v28.0.0 or later): Start the back-end
        container, which hosts a \textbf{FastAPI} (v0.114.1) service
        exposing Representational State Transfer (REST) endpoints for each pipeline phase, with the
        command \texttt{docker run -p 8000:8000 <image>}.
  \item \textbf{PICT}: Install the Microsoft PICT binary and ensure it
        is accessible on the system \texttt{PATH}. The tool invokes
        PICT as a subprocess during Phase~3.
  \item \textbf{Gemini API key}: Configure the key as an environment
        variable or enter it in the tool settings panel. The key is
        required for the LLM call in Phase~2.
  \item \textbf{Web browser}: Run \texttt{bash run\_tool.sh} to start
        the web interface server, then open a browser and navigate to
        \texttt{http://localhost:8080} to access the tool.
\end{enumerate}

\subsection{Supported Widgets}
The current version supports seven widget types, as detailed in
Table~\ref{tab:widgets} (Section~III). Five widget types act as PICT
factors (\texttt{TextFormField}, \texttt{DropdownButtonFormField},
\texttt{Radio}, \texttt{Checkbox}, \texttt{Switch}), one acts as a
fixed trigger (\texttt{ElevatedButton}), and one serves as an assertion
target (\texttt{Text}).

\subsection{PICT Model Construction}
For a screen with $n$ nonbutton widgets, the PICT model file contains
$n$ parameter lines of the form \texttt{<key>: v1, v2, \ldots, vk},
where each $v_i$ is a distinct value level. The tool builds three
separate model files---VI, V, and Edge---and invokes PICT once per
file. Each PICT run returns a minimal covering array; the three arrays
are concatenated to form the complete test suite for the screen. For a
\texttt{TextFormField} with five LLM-generated values (three valid, two
invalid), the corresponding PICT factor has five levels.
\texttt{DropdownButtonFormField} and \texttt{Radio} factors enumerate
all available options extracted from the source code.

\subsection{Implementation Constraints}
Each generated script covers \emph{one} application screen per
execution. Every target widget must carry a unique \texttt{Key}
property; widgets without a key are silently skipped. The LLM call
requires a valid Gemini API key at runtime, and PICT must be installed
and accessible on the system \texttt{PATH}.

\section{Evaluation}
% ===============================================

\subsection{Experimental Setup}
The tool was evaluated on three real-world Flutter applications: a
\textit{Medical Appointment} app, a \textit{Job Listing} app, and a
\textit{Real-Estate Listing} app. Two screens per application were
selected, yielding six screen-level evaluations in total. The test
environment used Flutter~v3.27.3 running on macOS Sequoia~15.4.1.
Statement coverage was measured using the Flutter \texttt{--coverage} flag
combined with \texttt{lcov} to filter results to UI page files only.

\subsection{Case Studies Overview}
The three applications represent increasing levels of form-validation
complexity. The \textit{Medical Appointment} app contains a booking
screen with nine input widgets (TextFormField, DropdownButtonFormField,
Radio, Switch) and a lighter search screen. The \textit{Job Listing} app includes a
posting screen with complex cross-field validation rules
(e.g., salary range constraints) and a search screen with a higher
widget count. The \textit{Real-Estate Listing} app presents two screens
of similar complexity, each combining text, dropdown, and toggle
widgets.

\subsection{Case Study 1: Medical Appointment Application}
The Medical Appointment application comprises an appointment-booking
screen with nine input widgets and a lighter search screen. The tool
generated 52 test cases (28~VI, 21~V, 3~Edge) for the booking screen
and 6 test cases (2~VI, 1~V, 3~Edge) for the search screen.
Fig.~\ref{fig:case_example} shows one of the generated VI cases as it
appears inside \texttt{<page>.test\_data.json} before being rendered
into a \texttt{testWidgets} block in \texttt{<page>\_test.dart}.

\subsection{Case Study 2: Job Listing Application}
The Job Listing application includes a posting screen with complex
mutual validation rules between fields (e.g., salary-range
constraints) and a search screen of comparable widget count. The tool
generated 64 test cases (31~VI, 30~V, 3~Edge) for the posting screen
and 63 test cases (30~VI, 30~V, 3~Edge) for the search screen,
demonstrating that pairwise coverage adapts naturally to screens with
dense cross-field constraints.

\subsection{Case Study 3: Real-Estate Listing Application}
The Real-Estate Listing application presents two screens of similar
complexity---posting and search---each combining text, dropdown, and
toggle widgets. The tool generated 55 test cases (27~VI, 25~V,
3~Edge) per screen, confirming that the tool produces a stable
case count for screens with comparable widget inventories.

\subsection{Coverage Results}
Table~\ref{tab:coverage} summarizes the statement coverage and test-case
counts across all six evaluated screens; Table~\ref{tab:reduction}
details the VI, V, and Edge breakdown per screen. All six screens
achieved statement coverage above \textbf{91\%}, and the highest result
(\textbf{96.6\%}, Real-Estate posting) was obtained despite a
reduced test-case count. Three characteristics of the generated
scripts contributed to this result: (i)~every widget interaction uses
\texttt{find.byKey}, providing a stable locator that tolerates UI
refactoring; (ii)~every nonempty \texttt{validatorRule} drives
exactly one invalid value plus one valid counterpart, ensuring each
validation branch in the Cubit is exercised at least once;
(iii)~both VI and V script groups are produced in a single invocation,
giving teams immediate coverage of positive and negative test paths.

% ===============================================
\section{Conclusion}
% ===============================================

This paper presented an automated tool for generating Flutter widget test
scripts using a combination of source-code metadata extraction, LLM-driven
synthetic data generation, and the Pairwise testing technique. The tool
requires no manual test-case authoring: developers supply only Flutter
front-end files and receive ready-to-run Dart test scripts as output.
Evaluation on three real-world mobile applications confirmed that the tool
successfully generates executable test scripts with measurable code coverage.

Current limitations include support for a fixed set of seven widget types,
a requirement that every target widget carries a unique \texttt{Key}
property (widgets without a key are silently skipped), a single-screen
scope per execution, and cases where expected results may not fully cover
all validation scenarios. Future work will extend widget support to
additional types, enable test-script generation from multiple source files
simultaneously, support more expressive constraint syntax for complex
cross-field rules, apply the approach to other mobile frameworks such as
React Native, Xamarin, and SwiftUI, support multiple back-end requests
within a single test case, and enable multi-screen end-to-end testing with
navigation linking between pages.
