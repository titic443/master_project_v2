\begin{abstract}
% -----------------------------------------------
In the software development lifecycle, unit testing is a critical process
for identifying and resolving defects, thereby enhancing software
reliability prior to delivery. This is particularly crucial in the rapidly
evolving domain of mobile applications developed with the Flutter framework,
where requirements change frequently. Although automated testing reduces
overall testing time, developers still require specialized knowledge and
significant initial effort to create effective test scripts in the Dart
language. This paper presents an automated tool that streamlines the
generation of Flutter test scripts by importing front-end source files,
extracting widget metadata (keys, validation conditions, and input-handling
types), and producing synthetic test data through a Large Language Model
(LLM). Test cases are systematically generated using the Pairwise testing
technique via the PICT tool. The resulting Dart test scripts are ready to
execute within the Flutter testing framework. The tool was evaluated against
three real-world mobile applications---a medical appointment system, a job
listing application, and a real-estate listing application---and achieved
satisfactory branch and line coverage in all cases, demonstrating the
practical effectiveness of the proposed approach.
\end{abstract}

\begin{IEEEkeywords}
Flutter, automated test generation, pairwise testing, Dart, large language
model, mobile application testing, PICT
\end{IEEEkeywords}

\section{Introduction}
% ===============================================

The global software industry continues to grow rapidly, driven by increasing
demand for mobile applications that are complex, feature-rich, and subject to
frequent requirement changes. Ensuring software quality through comprehensive
testing is therefore essential, yet designing test cases manually is
time-consuming and demands deep expertise from developers \cite{b1}.

Within the Flutter framework \cite{b1}, developers write integration and
widget test scripts in Dart to simulate user interactions on the user interface (UI). However,
crafting these scripts requires developers to (1) understand widget structure
and validation rules in the source code, (2) define appropriate input data
covering valid and invalid boundary conditions, and (3) sequence test actions
correctly. Existing automation tools such as Robot Framework and Playwright
are tailored for web applications and cannot directly generate Flutter-specific
test scripts.

This paper addresses these challenges by proposing an automated tool that:
\begin{itemize}
  \item Parses Flutter front-end (\texttt{.dart}) files to extract widget
        metadata;
  \item Uses a Large Language Model (LLM) (Google Gemini) to synthesize realistic test data;
  \item Applies the Pairwise testing technique through PICT to minimize the
        number of test cases while maximising input-combination coverage;
  \item Outputs executable Dart test scripts ready for the Flutter testing
        framework.
\end{itemize}

The remainder of this paper is organized as follows. Section~II reviews
related work. Section~III describes the proposed methodology. Section~IV
discusses tool design. Section~V presents evaluation results.
Section~VI illustrates a concrete generated test script, and Section~VII
concludes the paper.

% ===============================================
\section{Related Work}
% ===============================================

\subsection{Flutter Testing}
Flutter \cite{b1} is Google's open-source UI toolkit for building
cross-platform applications from a single Dart codebase. The framework
provides the \texttt{flutter\_test} library, which exposes a
\texttt{WidgetTester} application programming interface (API) and a rich set of Finders (\texttt{find.byKey},
\texttt{find.byType}, etc.) for locating and interacting with widgets during
testing.

\subsection{Test-Script Generation from Front-End Files}
Ekakrachawakitti \cite{b2} proposed a method for generating Robot Framework test
scripts from web front-end files by extracting HTML elements and input
constraints from a database schema. Srivichayanun \cite{b3} extended this concept
by importing XML Schema Definition (XSD) schemas and applying Boundary Value Analysis to produce test
data for web applications. These works motivate adapting similar extraction
techniques to Flutter's Dart-based widget structure.

\subsection{LLM-Based Data Generation}
Tuan Pham \cite{b4} demonstrated that structuring LLM prompts with distinct
components---context, persona, objective, action, format, and
refinement---significantly improves the quality of generated outputs. This
prompt-engineering strategy is adopted in the present work to drive synthetic
test-data generation.

\subsection{Pairwise Testing}
Pairwise (all-pairs) testing \cite{b7} is a black-box test-design technique
that ensures every pair of input-parameter values is exercised by at least one
test case, dramatically reducing the combinatorial explosion of full coverage.
PICT (Pairwise Independent Combinatorial Testing) \cite{b8} is a widely used
open-source tool that accepts a model file describing parameters and their
levels, and outputs a minimal covering test suite.

\subsection{Phase 1 -- Extract Manifest}

The tool statically analyzes every \texttt{.dart} file under the
\texttt{lib/} directory of the target Flutter project. Only widgets that
carry a \texttt{Key} property are considered, as the key is required to
locate a widget during test execution via \texttt{find.byKey()}.

At the \textit{screen level}, the tool records BLoC/Cubit metadata required
to construct the test environment: the page widget class name
(\texttt{pageClass}), the Cubit class (\texttt{cubitClass}), the associated
State class (\texttt{stateClass}), and the paths to the Cubit and State
source files (\texttt{fileCubit}, \texttt{fileState}). These fields allow
the generated test script to import the correct files and instantiate a
\texttt{BlocProvider} wrapper automatically.

At the \textit{widget level}, the tool records: (i)~the unique widget key,
(ii)~the widget class name, (iii)~allowed character or length patterns
from \texttt{inputFormatters}, (iv)~validation rules and error messages
parsed from \texttt{validator} callbacks (\texttt{validatorRules}), and
(v)~the selectable options list for \texttt{DropdownButtonFormField} and
\texttt{Radio} widgets.

The extracted metadata is serialized into a \texttt{manifest.json} file
grouped by screen name. Table~\ref{tab:manifest} lists the fields recorded
per screen and per widget.

\begin{table}[!t]
  \caption{Metadata Fields in the Manifest File}
  \label{tab:manifest}
  \centering
  \renewcommand{\arraystretch}{1.3}
  \begin{tabular}{lp{4.6cm}}
    \toprule
    \textbf{Field} & \textbf{Description} \\
    \midrule
    \multicolumn{2}{l}{\textit{Screen-level (BLoC metadata)}} \\
    \texttt{pageClass}      & UI page widget class name \\
    \texttt{cubitClass}     & BLoC Cubit class for the screen \\
    \texttt{stateClass}     & State class associated with the Cubit \\

    \midrule

    \texttt{key}            & Unique Flutter widget key \\
    \texttt{widgetType}     & Widget class name \\
    \texttt{inputFormatters}& Allowed character patterns and length limits \\
    \texttt{validatorRules} & Validation conditions and error messages \\
    \texttt{options}        & Enumerated choices for Radio / Dropdown \\
    \bottomrule
  \end{tabular}
\end{table}

\subsection{Phase 2 -- Generate Datasets}

Given the manifest, the tool constructs a structured LLM prompt following
the CO-STEP (Context, Objective, Style, Target, Execution, Polish)
framework \cite{b4}, which organizes the prompt into six
components: \textit{context} (describes the Flutter screen under test and
its widget validation structure), \textit{objective} (requests valid and
invalid value pairs for each \texttt{TextFormField}, one pair per
non-empty validation rule), \textit{style} (enforces a
JavaScript Object Notation (JSON)-only output schema with realistic,
typeable values and no markdown), \textit{target} (instructs the model to
act as a QA engineer generating happy-path and error-path data),
\textit{execution} (provides step-by-step instructions for counting
non-empty validation rules and constructing $N$ valid/invalid pairs), and
\textit{polish} (embedded via few-shot examples that constrain output
format and prevent hallucinated values). The widget metadata extracted in
Phase~1 is appended as the \textit{input data} payload.

The prompt is submitted to \textit{Google Gemini gemini-2.5-flash}
\cite{b5} via the Gemini API (HTTP POST). The model returns a
\texttt{<page>.datasets.json} file with the following top-level
structure:
\begin{itemize}
  \item \textbf{file:} path to the front-end source file that was
        analyzed.
  \item \textbf{datasets $\to$ byKey:} a map from each
        \texttt{TextFormField} widget key to an array of value-pair
        objects. Each object contains \texttt{valid} (a value that
        satisfies all validation rules), \texttt{invalid} (a value that
        violates exactly one rule while still conforming to
        \texttt{inputFormatters}), and \texttt{invalidRuleMessages}
        (the specific error message that would be triggered). One
        pair is generated per non-empty validation rule.
\end{itemize}
\texttt{Dropdown} and \texttt{Radio} widgets are not sent to the LLM;
their factor levels are drawn directly from the \texttt{options} list
extracted in Phase~1, ensuring complete enumeration coverage without
LLM hallucination risk.

\subsection{Phase 3 -- Generate Test Data}

Using the datasets, the tool constructs a PICT model file in which each
non-button widget maps to one \textit{factor} and each distinct value maps
to one \textit{level}. Three model variants are built independently:
\begin{enumerate}
  \item \textbf{Valid/Invalid (VI):} factors contain both valid and invalid
        levels; PICT ensures every valid--invalid pair is covered.
  \item \textbf{Valid-only (V):} factors contain valid levels only; PICT
        produces positive-path test cases.
  \item \textbf{Edge:} three manually crafted boundary-value combinations
        (empty input, maximum-length, special characters) are appended.
\end{enumerate}

PICT is invoked as a subprocess once per model file
(\texttt{<page>.full.model.txt} for VI and
\texttt{<page>.valid.model.txt} for V). Its tab-delimited
output---one row per test case---is parsed, and each row is assembled
into a \textit{case} object together with the widget interaction steps
and expected assertions. The three result arrays (VI, V, Edge) are then
merged into a single \texttt{<page>.test\_data.json} file that contains
three top-level keys:
\begin{itemize}
  \item \textbf{source:} the screen-level BLoC metadata propagated from
        Phase~1 (\texttt{pageClass}, \texttt{cubitClass},
        \texttt{stateClass}, \texttt{fileCubit}, \texttt{fileState}).
        Phase~4 reads this key to emit \texttt{import} statements and
        instantiate the \texttt{BlocProvider} wrapper.
  \item \textbf{datasets:} the valid/invalid value pairs produced in
        Phase~2, keyed by widget key (\texttt{byKey}). Phase~4 reads
        this key to resolve concrete values when rendering
        \texttt{enterText} calls.
  \item \textbf{cases:} the ordered list of test-case objects. Each
        object carries five fields: \texttt{tc} (a unique identifier
        such as \texttt{pairwise\_valid\_invalid\_cases\_1}),
        \texttt{kind} (\texttt{success} or \texttt{failed}),
        \texttt{group} (one of \texttt{pairwise\_valid\_invalid\_cases},
        \texttt{pairwise\_valid\_cases}, or \texttt{edge\_cases}),
        \texttt{steps}, and \texttt{asserts}.
\end{itemize}

Each \texttt{steps} entry maps widget type to a
\texttt{WidgetTester} command: \texttt{enterText} (with
\texttt{byKey} and a \texttt{dataset} reference) for
\texttt{TextFormField}; \texttt{tap} (byKey) then \texttt{tapText}
(item label) for \texttt{DropdownButtonFormField}; \texttt{tap}
(byKey) for \texttt{Radio}, \texttt{Checkbox}, and \texttt{Switch};
and \texttt{pump} or \texttt{pumpAndSettle} for UI refresh. Widget
steps are ordered by a \texttt{sequence} value extracted from the
source file, with the \texttt{ElevatedButton} step always placed last.
Each \texttt{asserts} entry specifies either a \texttt{text}
string with an \texttt{exists} flag (verifying a visible error message)
or a \texttt{byKey} widget identifier with an \texttt{exists} flag
(verifying the presence of a success or failure indicator widget).

\subsection{Phase 4 -- Generate Test Script}

The \texttt{<page>.test\_data.json} produced in Phase~3 is rendered
into a syntactically valid Dart test file named
\texttt{<page>\_test.dart}. The \texttt{TestScriptGenerator} class
first reads the \textbf{source} key to emit three \texttt{import}
statements (\texttt{fileCubit}, \texttt{fileState}, and the page
source file) and to declare a
\texttt{BlocProvider\textless CubitClass\textgreater} wrapper that is
reused across all test cases on the same screen.

Test cases are partitioned by their \texttt{group} field into three
\texttt{group()} blocks in the output file:
\texttt{pairwise\_valid\_invalid\_cases} (VI cases that verify form
rejection on invalid input), \texttt{pairwise\_valid\_cases} (V cases
that verify successful submission on valid input), and
\texttt{edge\_cases} (boundary-value cases). Each entry in the
\texttt{cases} array becomes one independent \texttt{testWidgets}
block named after its \texttt{tc} identifier. The block is structured
as follows:
\begin{enumerate}
  \item \textbf{Setup:} \texttt{tester.pumpWidget()} pumps a
        \texttt{MaterialApp} with the page wrapped in the
        \texttt{BlocProvider} declared from \texttt{source} metadata.
  \item \textbf{Interact:} each \texttt{steps} entry is translated
        to the corresponding \texttt{WidgetTester} call in sequence
        order---\texttt{enterText} resolves its value from the
        \texttt{datasets} key; \texttt{tap} and \texttt{tapText}
        locate widgets by key or label text; \texttt{pump} and
        \texttt{pumpAndSettle} synchronise the UI between interactions.
  \item \textbf{Assert:} each \texttt{asserts} entry is rendered as
        an \texttt{expect()} call. A \texttt{text}-based entry becomes
        \texttt{expect(find.text(`msg'),} \texttt{findsOneWidget)} and
        a \texttt{byKey}-based entry becomes
        \texttt{expect(find.byKey(Key(`k')),} \texttt{findsOneWidget)};
        the matcher switches between \texttt{findsOneWidget} and
        \texttt{findsNothing} according to the \texttt{exists} flag.
\end{enumerate}
The \texttt{ElevatedButton} step is always the last interaction,
followed by \texttt{pumpAndSettle()}, ensuring all asynchronous UI
updates settle before the assertions execute.

\section{Tool Design and Implementation}
% ===============================================

\subsection{Architecture}
The tool adopts a client--server architecture. The back end is implemented as
a \textbf{FastAPI} (v0.114.1) service running inside a \textbf{Docker}
(v28.0.0) container, exposing REST endpoints for each pipeline step. The
front end is a desktop graphical user interface (GUI) application that guides the user through three
inputs: (1) the Flutter front-end file(s), (2) an optional condition JSON
file for custom validation rules, and (3) an output directory path.

\subsection{PICT Model Construction}
For a screen with $n$ non-button widgets, the PICT model file contains $n$
parameter lines of the form \texttt{<key>: v1, v2, \ldots, vk}, where each
$v_i$ is a distinct value level. The tool builds three separate model
files---VI, V, and Edge---and invokes PICT once per file. Each PICT run
returns a minimal covering array; the three arrays are concatenated to form
the complete test suite for the screen. For a \texttt{TextFormField} with
five LLM-generated values (three valid, two invalid), the corresponding
PICT factor has five levels. \texttt{DropdownButtonFormField} and
\texttt{Radio} factors enumerate all available options extracted from the
source code.

\subsection{Implementation Constraints}
Each generated script covers \emph{one} application screen per execution.
Every target widget must carry a unique \texttt{Key} property; widgets
without a key are silently skipped. The LLM call uses the Gemini API and
requires an API key at runtime. PICT must be installed on the host system
and accessible on the \texttt{PATH}.

\section{Evaluation}
% ===============================================

\subsection{Experimental Setup}
The tool was evaluated on three real-world Flutter applications: a
\textit{Medical Appointment} app, a \textit{Job Listing} app, and a
\textit{Real-Estate Listing} app. Two screens per application were selected,
yielding six screen-level evaluations in total. The test environment used
Flutter~v3.27.3 running on macOS Sequoia~15.4.1. Line coverage was measured
using the Flutter \texttt{--coverage} flag combined with \texttt{lcov} to
filter results to UI page files only.

The appointment-booking screen exposes seven input widgets. The tool
generated 52 test cases (28 pairwise valid/invalid, 21 pairwise valid, and 3
edge cases) for the booking screen, and 6 test cases for the lighter search
screen. Fig.~\ref{fig:result_medical} shows an excerpt of the generated Dart

\section{Generated Test Script Example}
% ===============================================

This section illustrates the concrete Dart test script produced by the
tool for the Medical Appointment application booking screen.
The tool generates two groups of scripts in a single run:
\textbf{pairwise\_valid\_invalid\_cases} mixes valid and invalid values
across widget pairs to verify that the application correctly rejects
erroneous input, while \textbf{pairwise\_valid\_cases} uses only valid
values to verify the happy-path flow.

\subsection{Script Structure}
Each generated \texttt{.dart} file follows a fixed skeleton:
(i)~a \texttt{testWidgets} block named after its pairwise-combination
index, (ii)~widget-pump setup via \texttt{MaterialApp} and
\texttt{MultiBlockProvider}, and (iii)~a sequential interaction body
that mirrors the UI flow of the target screen.
Listing~\ref{lst:example} shows an abbreviated excerpt of one
\texttt{pairwise\_valid\_invalid\_cases} test case.

\begin{lstlisting}[caption={Abbreviated Dart test script -- \texttt{pairwise\_valid\_invalid\_cases\_1} (Medical Appointment screen).}, label=lst:example, captionpos=b, float=!t]
testWidgets('pairwise_valid_invalid_cases_1',
    (tester) async {
  final w = MaterialApp(
    home: MultiBlockProvider(
      providers: providers,
      child: ClinicAppointmentPage()));
  await tester.pumpWidget(w);

  // INVALID: patient name too short (1 char)
  await tester.enterText(
    find.byKey(Key('apt_01_patient_name_textfield')),
    'a');
  await tester.pump();

  // INVALID: ID card only 11 digits (expects 13)
  await tester.enterText(
    find.byKey(Key('apt_02_id_card_textfield')),
    '12345678901');
  await tester.pump();

  // VALID: select department via Dropdown
  await tester.ensureVisible(
    find.byKey(Key('apt_B1_id_department_dropdown')));
  await tester.tap(
    find.byKey(Key('apt_B1_id_department_dropdown')));
  await tester.pumpAndSettle();
  await tester.tap(find.text('Neuros', last));
  await tester.pumpAndSettle();

  // VALID: pick date via DatePicker dialog
  await tester.tap(
    find.byKey(Key('apt_B8_date_textfield')));
  await tester.pumpAndSettle(
    Duration(milliseconds: 5000));
  final editIcon =
    find.byKey(Key('DatePicker_edit_icon'));
  if (tester.any(editIcon)) {
    await tester.tap(editIcon.first);
    await tester.pumpAndSettle();
  }
  final dateField = find.descendant(
    of: find.byType(Dialog),
    matching: find.byType(TextField));
  await tester.enterText(
    dateField.first, '01/15/2001');
  await tester.pumpAndSettle();
  await tester.tap(find.text('OK'));
  await tester.pumpAndSettle();

  // Tap submit button (always last)
  await tester.tap(
    find.byKey(Key('apt_B9_button')));
  await tester.pumpAndSettle();
});
\end{lstlisting}

\subsection{Full Script Output}
Fig.~\ref{fig:script_output} shows the complete
\texttt{pairwise\_valid\_cases} output file as rendered by the tool

\subsection{Key Observations}
Three characteristics of the generated scripts are noteworthy.
First, every widget interaction uses \texttt{find.byKey}, providing a
stable locator that is independent of widget text or position and
tolerates UI refactoring without breaking the test.
Second, the \texttt{DatePicker} interaction is fully automated: the
tool injects a mode-switch step (tap the edit icon) before entering
the date string, eliminating a common source of flaky tests in
calendar-dialog scenarios.
Third, both valid-only and valid/invalid script groups are produced in
a single invocation, giving teams immediate coverage of positive and
negative test paths with no additional authoring effort.

% ===============================================
\section{Conclusion}
% ===============================================

This paper presented an automated tool for generating Flutter widget test
scripts using a combination of source-code metadata extraction, LLM-driven
synthetic data generation, and the Pairwise testing technique. The tool
requires no manual test-case authoring: developers supply only Flutter
front-end files and receive ready-to-run Dart test scripts as output.
Evaluation on three real-world mobile applications confirmed that the tool
successfully generates executable test scripts with measurable code coverage.

Current limitations include support for a fixed set of seven widgets, a
single-screen scope per run, and a dependency on the Gemini API for data
synthesis. Future work will extend widget support, enable multi-screen
scenario testing, investigate alternative open-source LLMs for offline use,
and incorporate feedback loops to refine generated test data based on
execution results.
